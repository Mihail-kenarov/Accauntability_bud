# Daily Life Coach Agent — Design Spec
**Date:** 2026-04-30  
**Status:** Draft

---

## 1. Design Challenge

> Design a **conversational life coach web agent** to enable **busy students** in **managing a demanding and irregular daily schedule** to **plan their day realistically and stay accountable to their personal goals** with **consistent improvement in training frequency, time management, and self-awareness over multiple weeks**.

---

## 2. Architecture Overview

```
┌─────────────────────────────────────────────────────────┐
│                    Streamlit Web UI                      │
│         (chat interface, mobile-accessible)              │
└───────────────────────┬─────────────────────────────────┘
                        │ user message
                        ▼
┌─────────────────────────────────────────────────────────┐
│                  LangChain Agent                         │
│  - Selects and calls tools based on user message         │
│  - Constructs prompt with retrieved context              │
│  - Sends to Ollama LLM                                   │
└───────┬──────────────┬──────────────┬───────────────────┘
        │              │              │
        ▼              ▼              ▼
┌──────────────┐ ┌──────────┐ ┌─────────────────┐
│ Google       │ │ ChromaDB │ │  Habit Tracker   │
│ Calendar API │ │ (Vector  │ │  (SQLite)        │
│              │ │  Store)  │ │                  │
│ - Today's    │ │ - User   │ │ - Daily logs     │
│   events     │ │   facts  │ │ - Habit streaks  │
│ - Free slots │ │ - Past   │ │ - Completion     │
│              │ │   logs   │ │   rates          │
└──────────────┘ └──────────┘ └─────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────────┐
│                  Ollama LLM                              │
│          (ministral-3:8b or mistral:7b, local)              │
└─────────────────────────────────────────────────────────┘
```

**Why two storage backends?**
- **ChromaDB** handles *semantic* memory — facts and logs retrieved by meaning, not exact match. When the agent needs "what do I know about this user's training habits?", it does a similarity search.
- **SQLite** handles *structured* memory — exact numbers like streak counts, completion rates, dates. These need precise queries, not semantic search.

## 4. Database Design

### 4.1 ChromaDB Collections

ChromaDB stores documents as text with metadata, retrieved by semantic similarity.

#### Collection: `user_facts`
Stores everything the agent learns about the user from conversation.

| Field | Type | Description |
|---|---|---|
| `document` | str | The fact in plain English ("user wants to train 4x per week") |
| `fact_type` | metadata str | `goal` / `preference` / `schedule_pattern` / `constraint` / `habit` |
| `source` | metadata str | The raw user message it was extracted from |
| `timestamp` | metadata str | ISO datetime of extraction |
| `confidence` | metadata float | 0.0–1.0, set by extraction LLM |

**Example documents:**
```
"User's daily calorie goal is 1600 kcal"            [goal]
"User does BJJ on Tuesday and Thursday evenings"    [schedule_pattern]
"User bikes to university most mornings"             [preference]
"User wants to wake up and read before checking phone" [goal]
"User sometimes works from 6am to 3pm"              [constraint]
"User goes to girlfriend's place on Friday evenings" [schedule_pattern]
```

**Retrieval:** When building a plan, the agent queries this collection with prompts like "training schedule", "work hours", "goals" to pull the most relevant facts.

---

#### Collection: `conversation_logs`
Stores summaries of each interaction session for long-term recall.

| Field | Type | Description |
|---|---|---|
| `document` | str | Summary of the session (generated by LLM) |
| `session_type` | metadata str | Label set by agent: `morning_plan` / `midday_checkin` / `evening_reflection` / `general` |
| `date` | metadata str | YYYY-MM-DD |
| `timestamp` | metadata str | ISO datetime |
| `habits_mentioned` | metadata str | Comma-separated habits discussed (for filtering) |

**Example document:**
```
"Evening check-in on 2026-04-29. User did not train today, citing tiredness after 
work. Planned to go to BJJ but skipped. User ate around 1800 kcal, over goal. 
Mood was low. User wants to train tomorrow morning instead."
[session_type: evening_reflection, date: 2026-04-29]
```

---

### 4.2 SQLite Tables

#### Table: `habit_logs`
One row per habit per day — the source of truth for streaks.

```sql
CREATE TABLE habit_logs (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    date        TEXT NOT NULL,          -- YYYY-MM-DD
    habit_name  TEXT NOT NULL,          -- 'training', 'calories_on_target', 'morning_read'
    completed   INTEGER NOT NULL,       -- 1 = yes, 0 = no, -1 = not logged
    notes       TEXT,                   -- optional free-text from user
    logged_at   TEXT NOT NULL           -- ISO datetime
);
```

#### Table: `daily_plans`
Stores the morning plan generated each day for later comparison.

```sql
CREATE TABLE daily_plans (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    date        TEXT NOT NULL,          -- YYYY-MM-DD
    plan_text   TEXT NOT NULL,          -- full plan as generated
    created_at  TEXT NOT NULL,          -- ISO datetime
    calendar_snapshot TEXT             -- JSON of calendar events used to build plan
);
```

#### Table: `habit_streaks`
Aggregated streak data, updated at each evening check-in.

```sql
CREATE TABLE habit_streaks (
    habit_name      TEXT PRIMARY KEY,
    current_streak  INTEGER DEFAULT 0,
    longest_streak  INTEGER DEFAULT 0,
    total_completed INTEGER DEFAULT 0,
    total_logged    INTEGER DEFAULT 0,
    last_updated    TEXT
);
```

## 5. Workflows

### 5.1 Morning Planning Workflow

**Trigger:** User says something like "plan my day", "good morning", or any day-planning request.

```
Input:
  - User message (e.g. "plan my day, I work until 2 today")
  - Current date + time (system)

Process:
  1. Tool: get_calendar_events(today) → list of events + free time slots
  2. Tool: retrieve_user_facts(query="goals training schedule constraints") → top-k facts
  3. Tool: retrieve_past_logs(query="evening reflection carry-over plans", n_days=1) → what happened yesterday, any carry-overs
  4. Tool: get_habit_streaks() → current streaks to reference
  5. Build prompt:
       [system: you are a life coach]
       [context: user facts + calendar + yesterday's log + streaks]
       [user message]
  6. LLM generates time-blocked plan
  7. Tool: save_daily_plan(date, plan_text, calendar_snapshot)

Output:
  - Time-blocked daily plan (text in chat)
  - Plan saved to SQLite daily_plans table
  - Example:
      "Here's your day:
       07:30 — Bike to uni
       09:00-11:00 — Work block (lectures)
       12:00 — Lunch (~500 kcal suggested)
       14:00 — Work ends, 30min decompression
       15:00 — BJJ session (you haven't trained in 2 days)
       17:30 — Home, study block for NLP assignment
       20:00 — Dinner (~600 kcal)
       22:00 — Wind down, no music, read"
```

---

### 5.2 Fact Extraction Workflow

**Trigger:** Runs after *every* user message, in the background.

```
Input:
  - User message (any)

Process:
  1. LLM with extraction prompt:
       "Extract any facts about the user's goals, habits, schedule, or preferences 
        from this message. Return as JSON list of {fact, fact_type, confidence}. 
        Return empty list if nothing new."
  2. Filter: confidence > 0.7 AND not already in ChromaDB (deduplication via similarity check)
  3. Tool: store_user_facts(facts) → save to ChromaDB user_facts collection

Output:
  - Updated user_facts collection (silent, no user-facing output)
  - Deduplication: if a similar fact already exists with confidence > 0.85, skip
```

---

### 5.3 Mid-day Check-in Workflow

**Trigger:** User says something like "I skipped the gym", "just finished work early", or any mid-day update.

```
Input:
  - User message (e.g. "I skipped the gym, too tired", "just finished work early")

Process:
  1. Tool: get_daily_plan(today) → retrieve morning plan from SQLite
  2. Tool: retrieve_user_facts(query="energy levels preferences flexibility") → context
  3. Build prompt with: current plan + user message + user facts
  4. LLM generates adjusted advice or encouragement

Output:
  - Adjusted recommendation (text in chat)
  - Example:
      "You skipped gym — that's fine. You still have the evening. 
       BJJ starts at 19:00, which leaves you 2h at home first. 
       Even a 20-min home workout counts toward your streak. Want me to 
       adjust the rest of your day?"
```

---

### 5.4 Evening Reflection Workflow

**Trigger:** User says something like "how did I do today", "evening check-in", or describes what they did that day.

```
Input:
  - User message describing their day
  - Current date

Process:
  1. Tool: get_daily_plan(today) → what was planned
  2. Tool: get_habit_streaks() → current streaks
  3. Parse user's report: what did they complete vs. skip
  4. LLM extracts habit completion from free-text:
       "Did user train today? Did user stay on calories? Did user read this morning?"
       → {training: true/false, calories_on_target: true/false, morning_read: true/false}
  5. Tool: log_habit(date, habit_name, completed) × N habits
  6. Tool: update_habit_streaks(completions)
  7. Tool: save_conversation_log(session_type="evening_reflection", summary, habits)
  8. LLM generates reflection + accountability response

Output:
  - Reflection message with:
      - What went well
      - What slipped and honest acknowledgment
      - Streak update ("Training streak: 2 days 🔥")
      - One concrete suggestion for tomorrow
  - SQLite habit_logs and habit_streaks updated
  - Conversation summary saved to ChromaDB
```

---

### 5.5 Accountability Injection (Cross-cutting)

**Not a separate workflow** — this runs inside every LLM prompt construction.

```
Process:
  1. Tool: get_habit_streaks() → check for broken streaks or slipping patterns
  2. Tool: retrieve_past_logs(query="skipped training missed goals", n_days=7)
  3. If pattern detected (e.g. "skipped training 3 of last 5 days"):
       → inject accountability context into system prompt:
         "The user has skipped training 3 of the last 5 days. 
          Mention this naturally if relevant. Don't lecture — be direct and encouraging."

Output:
  - Agent proactively references patterns without user having to ask
```

## 6. LangChain Agent Tools (Full List)

### Plan creation vs. plan editing — same two tools

The agent always runs this sequence for anything plan-related:

```
1. get_daily_plan(date)          → returns existing plan, or None
2. [LLM generates new or modified plan using returned plan as context]
3. save_daily_plan(date, ...)    → upsert: creates if None, overwrites if exists
```

If no plan exists → fresh creation. If a plan exists → the LLM receives it as context and edits it. No separate "edit" tool needed.

---

### Tool Reference

| # | Tool | Signature | When called | What it does internally | Returns |
|---|---|---|---|---|---|
| 1 | `get_calendar_events` | `(date: str)` | Morning plan, any time context is needed | Calls Google Calendar API, filters events for that date | `[{title, start, end, duration_min}]` |
| 2 | `get_daily_plan` | `(date: str)` | Before any planning or editing | SELECT from `daily_plans` WHERE date=? | `plan_text: str` or `None` |
| 3 | `save_daily_plan` | `(date: str, plan_text: str, calendar_snapshot: str)` | After LLM generates or edits a plan | UPSERT into `daily_plans` — creates or overwrites | `"saved"` |
| 4 | `retrieve_user_facts` | `(query: str, k: int = 5)` | Morning plan, any time personalization needed | Embeds query, similarity search in ChromaDB `user_facts` | `[fact_str, ...]` |
| 5 | `store_user_fact` | `(fact: str, fact_type: str, confidence: float, source: str)` | Background, after every user message | Checks for near-duplicates (cosine > 0.85), inserts if new | `"stored"` or `"duplicate_skipped"` |
| 6 | `retrieve_past_logs` | `(query: str, n_days: int = 7)` | Morning plan (carry-overs), accountability injection | Filters ChromaDB `conversation_logs` by date range, similarity search within results | `[log_summary_str, ...]` |
| 7 | `save_conversation_log` | `(session_type: str, summary: str, habits_mentioned: list[str])` | End of any session | LLM summarizes session in 3–5 sentences, stores in ChromaDB `conversation_logs` | `"saved"` |
| 8 | `log_habit` | `(date: str, habit_name: str, completed: bool, notes: str)` | Evening reflection, after LLM extracts completions | INSERT into `habit_logs` | `"logged"` |
| 9 | `get_habit_streaks` | `()` | Morning plan (motivational context), evening reflection | SELECT from `habit_streaks`, returns all habits | `{habit_name: {current_streak, longest_streak, completion_rate}}` |
| 10 | `update_habit_streaks` | `(completions: dict[str, bool])` | Evening reflection, after `log_habit` | For each habit: completed → streak+1, skipped → reset to 0; writes to `habit_streaks` | `{habit_name: new_streak}` |

> **Note on `get_yesterday_evening_log`:** removed as a standalone tool. Replaced by `retrieve_past_logs(query="evening reflection carry-over plans", n_days=1)` — same result, more flexible.

---

### Habit streak tools as a sub-system

Tools 8, 9, and 10 form a self-contained habit tracking sub-system. The LLM never writes a streak number directly — it extracts *intent* from free text (did the user train?), and the tools do the math and write the records.

```
Evening message → LLM extracts {training: true, calories: false}
                → log_habit() × N habits
                → update_habit_streaks({training: true, calories: false})
                → get_habit_streaks() for display in response
```

## 7. Streamlit UI Design

- **Single chat interface** — one text input, conversation history displayed above
- **Sidebar** — shows today's habit streak summary and current plan at a glance
- **Mobile layout** — narrow column, large tap targets, no hover-only interactions
- **Session state** — Streamlit session state holds conversation history for the current session; ChromaDB + SQLite provide cross-session persistence

## 8. Validation Strategy

*The assignment asks: how do you ensure the app is trustworthy given LLM probabilistic output?*

### 8.1 Structured Output Enforcement
- Habit extraction (evening reflection) uses LangChain's structured output parser with a Pydantic schema — the LLM must return `{training: bool, calories_on_target: bool, morning_read: bool}`, not free text. Prevents hallucinated completions.

### 8.2 Calendar Data as Ground Truth
- Plans are always built on top of real calendar data. The LLM cannot suggest "go to the gym at 10am" if Google Calendar shows a lecture at that time. Factual scheduling is constrained, not generated.

### 8.3 Fact Deduplication + Confidence Threshold
- Extracted user facts only enter ChromaDB if confidence > 0.7 and no similar fact already exists (cosine similarity > 0.85). Prevents the agent from "learning" contradictory or low-quality facts.

### 8.4 Streak Data is Never LLM-Generated
- Habit streaks and completion logs are written directly by tool calls with parsed structured output — the LLM never writes a number directly into the database. The LLM extracts intent; the tool writes the record.

### 8.5 Prompt Consistency
- System prompt is fixed and version-controlled. The LLM's role, tone, and constraints don't drift between sessions.

### 8.6 Manual Correction
- User can always say "that's wrong, I did train yesterday" and the agent will run a correction tool to update the log. All data is correctable.
